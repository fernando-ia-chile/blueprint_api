Para quién es esto. Para el desarrollador que va a clonar el blueprint y publicar un microservicio nuevo. Asume C#/.NET y SQL; no asume conocimiento previo de este repo.

Cómo leerlo. Las secciones 1–3 son de lectura obligada una sola vez. Las secciones 4–10 son la referencia que abrirás cada vez que agregues un endpoint. La sección 14 es el tutorial: si tienes prisa, cópialo y adapta.

Convención

En todo el manual, Blueprint / Recurso son los nombres de ejemplo del repo base. Al clonar renombras Blueprint → MiServicio (ver README.md) y reemplazas la feature Recurso por la tuya. El tutorial usa Alumno (ERP Banner) como caso real.

Desarrollo local (sin Azure)

En Development, AzureAppConfig:Endpoint está vacío y App Config se omite. Define lo sensible con user-secrets:

Fundamento 3

Motor: Oracle vs SQL Server

El motor se elige en tiempo de ejecución con Database:Provider. Tu repositorio se escribe una sola vez contra System.Data.Common (DbConnection, DbCommand, DbParameter); la fábrica resuelve el driver concreto.

IDbConnectionFactory
 ├─ Provider            Oracle | SqlServer   (de DatabaseOptions)
 ├─ CommandTimeout      segundos
 ├─ CreateConnection()          → OracleConnection | SqlConnection
 ├─ PrepareStoredProcCommand()  → Oracle: BindByName = true ; SQL: no-op
 └─ AddRefCursor(cmd, name)     → Oracle: OracleParameter RefCursor OUT ; SQL: null

Los únicos archivos que using Oracle.ManagedDataAccess.Client / Microsoft.Data.SqlClient son OracleProviderAdapter.cs y SqlServerProviderAdapter.cs. No los toques desde tu repo.

Qué cambia entre motores

AspectoOracleSQL Server
Múltiples result setsCada uno es un OUT SYS_REFCURSORSELECT …; SELECT …; consecutivos
En el repoAddRefCursor(cmd, "C_ALUMNOS") por cada cursorEsas llamadas son no-op (devuelven null)
Binding de parámetrosPor nombre — requiere BindByName=true (lo hace la fábrica)Por nombre nativo
Parámetros de entradaP_TP_DOC (sin @)@P_TP_DOC — AddParameter acepta ambos estilos, define uno y sé consistente
Tipo de NUMBERllega como decimalint/decimal/bit según columna
Tres reglas de oro

1. Orden de parámetros: agrega todos los AddRefCursor antes que los escalares de salida (P_CODIGO, P_MENSAJE). En Oracle, NextResultAsync() recorre los cursores en el orden en que se agregaron.

2. OUT params después del reader: los valores de P_CODIGO/P_MENSAJE sólo están disponibles cuando el DbDataReader se cerró. Léelos fuera del bloque await using (var reader = …).

3. Orden canónico de result sets: define un orden (p. ej. Alumno → Programas → Semestres) y respétalo idéntico en el SP de Oracle y en el de SQL Server. Documéntalo en el XML-doc del método y en los .sql de db/.

Cómo cambiar de motor

# local
$env:Database__Provider = "Oracle"     # o "SqlServer"
dotnet run

# entorno desplegado: cambiar Blueprint:Database:Provider en App Configuration
# (con el label del entorno) y tocar Blueprint:Sentinel para refrescar.
Feature · paso a

Entidades

Una entidad es un POCO que representa una fila de un result set. Vive en AIEP.Domain.Data*/Entities. Sólo las propiedades con [Column("NOMBRE")] se mapean; el nombre debe coincidir con la columna del SP (sin distinguir mayúsculas).

AIEP.Domain.DataBlueprint/Entities/AlumnoEntity.cs 
using System.ComponentModel.DataAnnotations.Schema;

namespace AIEP.Domain.DataBlueprint.Entities;

public class AlumnoEntity
{
    [Column("PIDM")]              public int     Pidm { get; set; }
    [Column("ID_BANNER")]         public string? IdBanner { get; set; }
    [Column("RUT")]               public string? Rut { get; set; }
    [Column("NOMBRES")]           public string? Nombres { get; set; }
    [Column("APELLIDO_PATERNO")]  public string? ApellidoPaterno { get; set; }
    [Column("APELLIDO_MATERNO")]  public string? ApellidoMaterno { get; set; }
    [Column("EMAIL")]             public string? Email { get; set; }
    [Column("FECHA_NACIMIENTO")]  public DateTime? FechaNacimiento { get; set; }

    // 'Y'/'N' o 1/0 en la BD → bool en C#
    [Column("VIGENTE")]           public bool    Vigente { get; set; }

    // Propiedad de navegación: SIN [Column] ⇒ el mapper la ignora.
    // La llenas tú en el repositorio a partir de otro result set.
    public List<ProgramaAlumnoEntity> Programas { get; set; } = new();
}

Nombres de columna con Banner

Banner expone nombres crudos (SPRIDEN_PIDM, SPRIDEN_ID, SGBSTDN_STST_CODE). No los uses tal cual en la entidad: haz que el stored procedure devuelva alias limpios (PIDM, ID_BANNER, ESTADO) y mapea contra esos alias. La entidad queda legible y desacoplada del esquema físico.

Tipos y conversiones que soporta DbReaderMapper

Destino en C#Qué acepta de la BD
stringcualquier valor (usa ToString invariante si hace falta)
bool"Y"/"N", "1"/"0", "true"/"false", 1/0 numérico, bit
int/long/short/byte/decimal/doublenuméricos (incluye NUMBER de Oracle vía Convert.ChangeType)
DateTime, DateTimeOffset, TimeSpanfecha/hora del proveedor o texto parseable
GuidGuid, byte[] (16), o string
enumentero o nombre (case-insensitive)
T? (nullable)todo lo anterior; NULL/DBNull ⇒ queda el default de la propiedad
Nulos

Si la columna viene NULL, la propiedad no se asigna (mantiene su valor por defecto). Por eso un int no-nullable con valor NULL en la BD te dará 0: declara int? si "sin dato" es distinto de "cero".

El escaneo de [Column] y la compilación de setters se hace una vez por tipo y se cachea (ConcurrentDictionary + Expression). No hay costo de reflexión por fila.

Feature · paso b

Modelos (DTOs)

El DTO es el contrato con el cliente. Vive en AIEP.Application.Model/Models/<Feature>. Nunca expongas la entidad directamente: desacopla el JSON del esquema de BD y evitas filtrar campos internos (como PIDM).

DTO de salida — [JsonPropertyName]

AIEP.Application.Model/Models/Alumno/Alumno.cs 
using System.Text.Json.Serialization;

namespace AIEP.Application.Model.Models.Alumno;

public class Alumno
{
    [JsonPropertyName("RUT")]              public string? Rut { get; set; }
    [JsonPropertyName("Nombre Completo")]  public string? NombreCompleto { get; set; }
    [JsonPropertyName("Email")]            public string? Email { get; set; }
    [JsonPropertyName("Vigente")]          public bool    Vigente { get; set; }
    [JsonPropertyName("Programas")]        public List<ProgramaAlumno> Programas { get; set; } = new();
}

public class ProgramaAlumno
{
    [JsonPropertyName("Codigo")]  public string? Codigo { get; set; }
    [JsonPropertyName("Nombre")]  public string? Nombre { get; set; }
}

DTO de entrada — DataAnnotations

El request se recibe por [FromQuery] (o [FromBody]). [ApiController] valida las anotaciones automáticamente y responde 400 si fallan, antes de entrar a tu acción.

AIEP.Application.Model/Models/Alumno/AlumnoRequest.cs 
using System.ComponentModel.DataAnnotations;

namespace AIEP.Application.Model.Models.Alumno;

public class AlumnoRequest
{
    [Required]
    [StringLength(20, MinimumLength = 1)]
    public string? valorDocumento { get; set; }

    [Required]
    [RegularExpression("RUT|PASAPORTE|DNI")]
    public string? tipoDocumento { get; set; }
}
Regla

Entidad ≠ DTO aunque se parezcan. La entidad cambia cuando cambia el SP; el DTO cambia cuando cambia el contrato público. Mantenerlos separados es lo que te deja evolucionar uno sin romper el otro.

Feature · paso c

El mapper

Se usa AutoMapper. El perfil vive en el proyecto API (AIEP.Application.Api.*/Mapper/MapperConfig.cs) y se descubre por el escaneo de ensamblados en Program.cs:

builder.Services.AddAutoMapper(AppDomain.CurrentDomain.GetAssemblies());
Mapper/MapperConfig.cs 
using AIEP.Domain.DataBlueprint.Entities;
using AutoMapper;
using DtoAlumno = AIEP.Application.Model.Models.Alumno.Alumno;
using DtoPrograma = AIEP.Application.Model.Models.Alumno.ProgramaAlumno;

public class MapperConfig : Profile
{
    public MapperConfig()
    {
        // Registra el tipo anidado ANTES del contenedor.
        CreateMap<DtoPrograma, ProgramaAlumnoEntity>().ReverseMap();

        CreateMap<DtoAlumno, AlumnoEntity>()
            // nombres iguales se mapean solos; sólo declara lo que difiere
            .ForMember(d => d.Nombres, o => o.Ignore())
            .ReverseMap()
            .ForMember(d => d.NombreCompleto,
                       o => o.MapFrom(s => $"{s.Nombres} {s.ApellidoPaterno} {s.ApellidoMaterno}".Trim()));
    }
}
SituaciónQué hacer
Propiedades con el mismo nombreNada. Se mapean por convención.
Nombres distintos.ForMember(d => d.X, o => o.MapFrom(s => s.Y))
Colección anidada (List<ProgramaAlumno>)Registrar también CreateMap del tipo del elemento.
Ida y vuelta.ReverseMap(). Los ForMember posteriores aplican al mapa invertido.
Ignorar una propiedad.ForMember(d => d.X, o => o.Ignore())

En la lógica el mapeo es una línea:

return _mapper.Map<List<Alumno>>(entidades);
Pitfall

Si pones el Profile en otra capa, AddAutoMapper(GetAssemblies()) puede no escanearlo hasta que ese ensamblado se cargue. Mantén todos los Profile en el proyecto API. Para verificar todos los mapas en un test: new MapperConfiguration(c => c.AddProfile<MapperConfig>()).AssertConfigurationIsValid();

Feature · paso d

Repositorio

Hereda de BaseRepository e implementa tu interfaz. Un método público por operación. Todo async con CancellationToken y await using.

Anatomía de un método

AIEP.Application.Repository/Repository/Alumno/AlumnoRepository.cs 
public sealed class AlumnoRepository : BaseRepository, IAlumnoRepository
{
    private readonly string _sp;

    public AlumnoRepository(
        IDbConnectionFactory factory,
        IOptions<DatabaseOptions> dbOptions,
        IConfiguration configuration,
        ILogger<AlumnoRepository> logger)
        : base(factory, dbOptions, logger)
    {
        _sp = configuration.GetValue<string>("Conf:StoredProcedureName")
              ?? "PKG_BLUEPRINT.P_GET_ALUMNO";
    }

    public async Task<List<AlumnoEntity>> GetAlumnoAsync(
        string valorDocumento, string tipoDocumento, CancellationToken ct = default)
    {
        List<AlumnoEntity> alumnos;
        List<ProgramaAlumnoEntity> programas;

        await using var conn = await OpenConnectionAsync(ct);
        await using var cmd  = CreateStoredProcCommand(conn, _sp);

        AddParameter(cmd, "P_TP_DOC",    tipoDocumento,   DbType.String, size: 20);
        AddParameter(cmd, "P_DOCUMENTO", valorDocumento,  DbType.String, size: 20);

        // Cursores ANTES que los escalares OUT — orden canónico: #1 alumno, #2 programas
        AddRefCursor(cmd, "C_ALUMNO");
        AddRefCursor(cmd, "C_PROGRAMAS");

        AddParameter(cmd, "P_CODIGO",  null, DbType.String, ParameterDirection.Output, size: 4000);
        AddParameter(cmd, "P_MENSAJE", null, DbType.String, ParameterDirection.Output, size: 4000);

        await using (var reader = await cmd.ExecuteReaderAsync(ct))
        {
            alumnos   = await MapAsync<AlumnoEntity>(reader, ct);
            await reader.NextResultAsync(ct);
            programas = await MapAsync<ProgramaAlumnoEntity>(reader, ct);
        } // ← el reader se cierra aquí; recién ahora se pueden leer los OUT params

        ThrowIfSpError(GetOutputString(cmd, "P_CODIGO"), GetOutputString(cmd, "P_MENSAJE"));

        // Ensamblado 1→N en memoria
        var porPidm = programas.ToLookup(p => p.Pidm);
        foreach (var a in alumnos) a.Programas = porPidm[a.Pidm].ToList();

        return alumnos;
    }
}

Registrar el repo en DI

AIEP.Application.Repository/ServiceCollectionExtensions.cs 
public static IServiceCollection AddBlueprintRepository(this IServiceCollection services, IConfiguration configuration)
{
    services.AddOptions<DatabaseOptions>()
            .Bind(configuration.GetSection(DatabaseOptions.SectionName))
            .ValidateDataAnnotations();

    services.AddSingleton<IDbConnectionFactory, DbConnectionFactory>();

    services.AddScoped<IRecursoRepository, RecursoRepository>();
    services.AddScoped<IAlumnoRepository, AlumnoRepository>();   // ← agrega tu repo aquí

    return services;
}
Un SP con un solo result set

Es el caso simple: una llamada a MapAsync<T>, cero NextResultAsync. Los AddRefCursor siguen siendo uno (Oracle) o ninguno (da igual en SQL Server).

Feature · paso e

Lógica de negocio

Clase concreta (sin interfaz), registrada Scoped. Aquí van: validación de parámetros, reglas de negocio, orquestación de varios repos, y el mapeo entidad → DTO. No va acceso a datos directo.

AIEP.Application.Logic/Logic/AlumnoLogic.cs 
public class AlumnoLogic
{
    private readonly IAlumnoRepository _repo;
    private readonly IMapper _mapper;
    private readonly ILogger<AlumnoLogic> _logger;

    public AlumnoLogic(IAlumnoRepository repo, IMapper mapper, ILogger<AlumnoLogic> logger)
    {
        _repo = repo; _mapper = mapper; _logger = logger;
    }

    public async Task<List<Alumno>> GetAlumno(
        string? valorDocumento, string? tipoDocumento, CancellationToken ct = default)
    {
        if (string.IsNullOrWhiteSpace(valorDocumento))
            throw new RequiredParameterException(nameof(valorDocumento));   // → 400
        if (string.IsNullOrWhiteSpace(tipoDocumento))
            throw new RequiredParameterException(nameof(tipoDocumento));

        _logger.LogInformation("Consulta de alumno {Tipo}:{Doc}", tipoDocumento, valorDocumento);

        var data = await _repo.GetAlumnoAsync(valorDocumento, tipoDocumento, ct);
        return _mapper.Map<List<Alumno>>(data);
    }
}
CancellationToken

Propágalo siempre: controller → logic → repo → ExecuteReaderAsync(ct). Si el cliente corta la conexión, la consulta a la BD se cancela y no consumes un pool slot de más.

Feature · paso f

Endpoints

Controller MVC en Controllers/v1/, namespace ...Controllers.v1. Devuelve el DTO "pelado" (no hay envoltorio ApiResponse<T>).

Controllers/v1/AlumnoController.cs 
[ApiController]
[Route("api/v{version:apiVersion}/[controller]")]
[ApiVersion("1.0")]
[Authorize]
public class AlumnoController : ControllerBase
{
    private readonly AlumnoLogic _logic;
    private const string _scope = "IntegrationService.Blueprint.Read";

    public AlumnoController(AlumnoLogic logic) => _logic = logic;

    [HttpGet]
    [RequiredScope(AcceptedScope = new[] { _scope })]
    [TypeFilter(typeof(ExceptionHandler))]
    [RequireClaim("ClaimTenantId")]
    public async Task<IActionResult> Get([FromQuery] AlumnoRequest? request, CancellationToken ct)
    {
        var output = await _logic.GetAlumno(request?.valorDocumento, request?.tipoDocumento, ct);
        return Ok(output);
    }
}

Cada atributo, para qué

AtributoEfecto
[ApiController]Valida ModelState (DataAnnotations del request) ⇒ 400 automático; binding inferido.
[Route("api/v{version:apiVersion}/[controller]")]Ruta con segmento de versión. [controller] = nombre sin sufijo (Alumno).
[ApiVersion("1.0")]Versión que sirve este controller. Default asumido si no se especifica.
[Authorize]Exige JWT Bearer válido (Azure AD).
[RequiredScope(AcceptedScope = …)]El token debe traer ese scp/scope. Si no ⇒ 403.
[RequireClaim("ClaimTenantId")]El claim tid debe estar en Conf:ListTenantId. Si no ⇒ 403.
[TypeFilter(typeof(ExceptionHandler))]Envuelve la acción: cualquier excepción sale como ExceptionResponse con el HTTP correcto.

    throw new NotFoundException<string>($"No existe alumno {tipo}:{doc}.");
El cuerpo del error

ExceptionResponse { string message; string detail; }. En 400/404 el detail es la URL de la request; en 500 es un texto genérico (no filtra el stack). Todo se loguea con la excepción completa antes de responder.

Operación

Seguridad

Cuatro capas, en orden de ejecución:

  1. API key — ApiKeyMiddleware compara el header x-xmsbs-apikey contra Conf:ApiKey (de Key Vault, refrescable) y Conf:AdditionalKeys. Sin match ⇒ 401 texto plano. OPTIONS pasa directo.
  2. JWT Bearer — [Authorize] + AddMicrosoftIdentityWebApiAuthentication. Token de Azure AD (AzureAd en config, sin ClientSecret: sólo se validan tokens).
  3. Scope — [RequiredScope(...)]. El token debe traer IntegrationService.<Servicio>.Read (o el que definas).
  4. Tenant — [RequireClaim("ClaimTenantId")]. El claim tid debe estar en Conf:ListTenantId.

Rotación de API key sin downtime

Publica la key nueva en Conf:AdditionalKeys (array). Durante la ventana se aceptan la vieja (Conf:ApiKey) y la nueva. Luego promueve la nueva a Conf:ApiKey y vacía AdditionalKeys. Como se leen por IOptionsMonitor, el cambio en App Config entra sin reiniciar (refresco cada 5 min al tocar Blueprint:Sentinel).

Swagger con auth

El UI ya trae el botón Authorize (definición Bearer). Pega Bearer <token> y prueba endpoints protegidos. Swagger se sirve antes del ApiKeyMiddleware, así que /swagger no pide API key.

CORS

Política "CorsPolicy". Si AllowedHosts = "*" ⇒ abierto; si no, se restringe a Cors:AllowedOrigins. Ajusta esa lista por entorno.

Logging

NLog, configurado en nlog.config. En contenedor los logs salen como JSON a stdout (target jsonConsole) para Azure Monitor / docker logs; en disco sólo Error+.

Logueo estructurado — no interpoles

Infraestructura institucional (middleware)

Ningún microservicio nacido de este blueprint se expone directo a internet: todos pasan por la capa de integración institucional de AIEP —Cloudflare, Azure Application Gateway y Azure API Management— antes de llegar al backend. Lo que sigue es el resumen de alto nivel de esa arquitectura; el detalle de direccionamiento IP, VMs y puertos lo administra el equipo de Infraestructura.

Camino de una request, de internet al backend

Internet
   │
Cloudflare                     dominio público: services{dev|qa|prod}.aiep.cl (TLS / WAF)
   │
Azure Application Gateway      VNet "Hub-Integración"
   │
   ├─ VNet peered Desarrollo    → Azure Data Factory + API Management (API Gateway)
   ├─ VNet peered QA            → Azure Data Factory + API Management (API Gateway)
   └─ VNet peered Producción    → Azure Data Factory + API Management (API Gateway)
   │
VPN Site-to-Site               (Azure ⇄ on-premise)
   │
Servidor on-premise del entorno: balanceador + API Gateway autoalojado + IIS +
                                  SQL Server + Self-Hosted Integration Runtime
   │
Orígenes de datos: SQL Server on-premise · Oracle en OCI (primaria + réplica, un par por entorno)
EntornoDominio públicoRol
Desarrollo (DESA)servicesdev.aiep.clPrimer despliegue de un servicio nuevo; red, Data Factory y API Management propios.
QAservicesQA.aiep.clValidación previa a producción, aislada de Desarrollo en su propia red y API Management.
ProducciónservicesProd.aiep.clAmbiente productivo; red, API Management y par OCI dedicados.

Desarrollo (DESA)

Es donde llega un servicio apenas sale de desarrollo local. Tiene su propia red virtual peered en Azure (Data Factory + API Management) y su propio servidor on-premise (balanceador, API Gateway autoalojado, IIS, SQL Server, Integration Runtime). Las bases Oracle se sirven desde la réplica OCI compartida de Desarrollo/Test/QA. Dominio público: servicesdev.aiep.cl.

QA

Misma arquitectura que Desarrollo, pero en su propia red virtual y su propio API Management: las pruebas de un servicio no interfieren con el desarrollo en curso de otro. Comparte el par OCI de Desarrollo/Test/QA con una instancia lógica distinta. Dominio público: servicesQA.aiep.cl.

Producción

Red virtual, API Management y servidores on-premise dedicados; la base Oracle vive en el par OCI-Primaria/Réplica exclusivo de Producción. Dominio público: servicesProd.aiep.cl. El paso a Producción sigue el proceso de release del equipo de Infraestructura, no un despliegue directo del equipo de desarrollo.

Qué significa para tu servicio

El Database:Provider y la cadena de conexión de tu blueprint apuntan a la base del entorno donde despliegas (SQL Server on-premise u Oracle en OCI). El nombre público que consumirán los clientes sigue el patrón services{entorno}.aiep.cl; TLS y WAF ya los resuelve Cloudflare + Application Gateway antes de llegar a tu API.

Alcance de este resumen

Es intencionalmente de alto nivel: no incluye direccionamiento IP, nombres de VM ni puertos. Para el detalle de red, o para solicitar una integración nueva, contacta al equipo de Infraestructura.

Aristas frecuentes / FAQ

Paginación

El blueprint no la trae. Patrón recomendado: parámetros @P_PAGINA/@P_TAMANO al SP + un tercer result set (o un OUT param) con el total. En el DTO, un envoltorio PagedResult<T> { items, page, size, total } — este sí es un caso legítimo de envoltorio.

Transacciones

No hay soporte en BaseRepository (los SP de sólo-lectura no lo necesitan). Si escribes: abre la conexión, await using var tx = await conn.BeginTransactionAsync(ct), asigna cmd.Transaction = tx, y await tx.CommitAsync(ct). Mantenlo dentro de un único método del repo.

Varios SP o varias conexiones en un método

Abre una DbConnection por SP (o reusa la misma para varios comandos secuenciales). Si necesitas dos bases distintas a la vez, usa la variante de dos claves de conexión (ConnectionStrings:BlueprintDb.Oracle / .SqlServer) y resuelve la segunda con IConfiguration.GetConnectionString directamente.

Consultas largas

Database:CommandTimeout (segundos) aplica a todos los comandos. Para un SP puntualmente lento, súbelo por entorno en App Config; no lo bajes globalmente.

Performance con muchos registros

DbReaderMapper ya lee la fila completa con GetValues y cachea los setters. Para volúmenes grandes en Oracle, sube FetchSize en la cadena o en el comando (((OracleCommand)cmd).FetchSize dentro de un adapter). Evita traer miles de filas por endpoint: pagina.

Health checks

No incluidos (paridad con Sedes). Para agregarlos: builder.Services.AddHealthChecks().AddCheck(...) con un ping a SELECT 1 / SELECT 1 FROM DUAL vía IDbConnectionFactory, y app.MapHealthChecks("/health") antes del ApiKeyMiddleware.

OpenTelemetry / métricas

No incluido. Punto de extensión natural en Program.cs junto al logging; el ExceptionHandler ya centraliza el registro de fallos.

Qué NO hacer

  • Leer IConfiguration crudo en Logic o Controller — usa IOptions.
  • using Oracle.* / using Microsoft.Data.SqlClient fuera de los dos adapters.
  • Devolver la entidad *Entity desde el controller — siempre el DTO.
  • Capturar Exception en el repo para "loguear y relanzar" — deja que suba al ExceptionHandler.
  • Leer P_CODIGO con el reader abierto.
  • Interpolar strings en los logs.
